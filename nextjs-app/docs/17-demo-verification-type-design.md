# 데모 검증 유형 분석 및 개선 설계

241개 데모의 `[검증]`을 하나의 `기대 결과 vs 실제 측정값` 형식에 맞추지 않고, 각 데모에서 실제로 확보할 수 있는 증거와 확인 방식에 맞게 재설계하기 위한 기획 문서다.

이 문서는 최종 컴포넌트 API를 확정하지 않는다. 먼저 241개 데모를 같은 기준으로 분석한 뒤, 실제 분포와 예외를 근거로 최종 검증 유형과 UI를 결정한다.

## 1. 배경

모든 데모는 `[가이드] → [데모 예제] → [검증] → [개념 정리]`의 네 섹션을 사용한다. 학습자는 가이드 절차대로 데모를 조작한 뒤 검증 섹션에서 결과를 확인한다.

현재 `ExpectedActualPanel`은 241개 데모에 존재하지만, 정적 조사 결과 218개가 `실시간 인터랙션 및 상태 동기화 완료` 같은 공통 문구를 실제값으로 사용한다. 이 구조는 다음 사례를 구분하지 못한다.

- HTTP 상태나 URL처럼 기대값과 실제값을 직접 비교할 수 있는 데모
- 캐시 ID나 컴포넌트 생명주기처럼 실행 전후 변화를 확인해야 하는 데모
- 레이아웃 유지나 포커스 이동처럼 화면을 직접 관찰해야 하는 데모
- 설정 파일이나 빌드 산출물을 확인해야 하는 데모
- Network, 콘솔, 서버 로그 또는 배포 환경에서 확인해야 하는 데모

## 2. 목표와 비목표

### 목표

- 241개 데모의 검증 항목과 확보 가능한 증거를 전수 조사한다.
- 증거와 확인 방식에 따라 검증 유형을 도출한다.
- 데모별 대표 검증 유형과 세부 검증 항목을 구조화된 목록으로 만든다.
- 네 섹션의 정합성과 수정 필요 여부를 함께 판정한다.
- 후속 구현에서 유형별 공통 UI와 데모별 수정 범위를 결정할 근거를 제공한다.

### 비목표

- 이 문서 작성 단계에서 검증 컴포넌트나 데모 코드를 변경하지 않는다.
- 초기 후보 유형을 최종 유형으로 고정하지 않는다.
- 측정할 수 없는 결과를 성공 문구나 간접 표현으로 통과 처리하지 않는다.

## 3. 분류 원칙

검증 유형은 `라우팅`, `캐시`, `Server Action` 같은 Next.js 기능군이나 `클릭`, `입력` 같은 사용자 조작으로 나누지 않는다. **어떤 증거를 어디에서 확보하고, 어떤 방식으로 확인하는가**를 기준으로 나눈다.

한 데모에는 집계와 작업 배치를 위한 **대표 검증 유형** 하나를 지정한다. 다만 하나의 데모가 값 비교와 화면 관찰을 함께 포함할 수 있으므로 `[검증]` 안에는 서로 다른 유형의 **검증 항목**을 여러 개 허용한다.

확인 위치만 다른 경우에는 별도 유형으로 만들지 않고 `증거 위치`로 기록한다. 예를 들어 HTTP 상태를 데모 화면에서 보든 Network에서 보든 판정 방식은 값 비교일 수 있다.

## 4. 초기 후보 유형

| 후보 유형 | 확인 방식 | 대표 증거 | 예시 |
|---|---|---|---|
| 값 비교 | 기대 조건과 실제값을 직접 비교 | 응답 값, HTTP 상태, URL, pathname, 헤더, 쿠키 | Route Handler 응답 코드가 201인지 확인 |
| 전후 변화 | 조작 전후 값이나 이벤트 순서를 비교 | 캐시 ID, 타임스탬프, 렌더 횟수, 라우트 이력 | 무효화 전후 캐시 ID가 달라지는지 확인 |
| 화면 관찰 | 수치 판정 없이 성공 단서를 직접 관찰 | 레이아웃, 로딩 UI, 포커스, 모달, 스크롤 | 하위 경로 이동 중 상위 레이아웃이 유지되는지 관찰 |
| 산출물·설정 확인 | 소스나 실행 산출물의 존재와 내용을 확인 | 설정 파일, manifest, 빌드 폴더, 번들 결과 | `.next/standalone` 산출물 생성 여부 확인 |
| 외부 도구·환경 확인 | 데모 화면 밖의 실행 증거를 확인 | Network, 콘솔, 서버 로그, CLI, 배포 환경 | Server Action POST 요청을 Network에서 확인 |

이 표는 전수 분석을 시작하기 위한 가설이다. 분석을 마친 뒤 다음 규칙으로 최종 유형을 확정한다.

- 같은 확인 절차와 같은 UI 구조를 공유하면 병합한다.
- 한 유형 안에서 판정 방식과 필요한 정보가 명확하게 갈리면 분리한다.
- 사용 사례가 없거나 별도 UI가 필요하지 않으면 제거한다.
- 외부 도구·환경 확인이 독립 유형이 아니라 증거 위치에 불과한지 별도로 검토한다.

## 5. 분석 결과 상태

검증 유형과 실행 결과를 혼동하지 않는다. 각 검증 항목은 다음 중 하나로 판정한다.

| 결과 | 의미 |
|---|---|
| `pass` | 기대 조건을 충족하는 증거를 확보했다 |
| `fail` | 증거를 확보했지만 기대 조건과 일치하지 않는다 |
| `observe` | 자동 판정하지 않고 명시된 화면 변화를 관찰한다 |
| `unverifiable` | 현재 데모와 환경에서 유효한 증거를 확보할 수 없다 |
| `execution-error` | 절차 실행 중 오류가 발생해 판정을 완료하지 못했다 |
| `blocked-by-environment` | 필요한 빌드·도구·배포 환경이 없어 실행하지 못했다 |

`검증 불가`는 별도의 검증 유형이 아니다. 어떤 유형을 적용하려 했으나 현재 조건에서 증거를 얻지 못한 분석 결과다. 검증 불가인 경우 사유, 필요한 환경, 데모 재설계 여부와 기대 문구 축소 여부를 기록한다.

## 6. 수정 필요 판정

### `[가이드]`

- 실제 화면에 없는 버튼이나 라벨을 지시한다.
- 실행 순서가 실제 동작과 맞지 않는다.
- 관찰 대상이나 관찰 위치가 불명확하다.
- 초기화, 새로고침 또는 외부 도구 사용 조건이 빠져 있다.

### `[데모 예제]`

- 가이드대로 실행되지 않는다.
- 실제 Next.js 기능이 아닌 로컬 상태로 동작을 흉내 낸다.
- 검증에 필요한 신호를 제공하지 않는다.
- 초기화가 불완전하거나 환경에 따라 실행이 깨진다.

### `[검증]`

- 측정하지 않은 값을 실제 측정값이라고 표시한다.
- 고정 성공 문구나 근거 없는 통과 배지를 표시한다.
- 화면 관찰형 동작을 값 비교 형식에 억지로 넣는다.
- 외부 증거가 필요한데 화면 안에서 검증된 것처럼 표현한다.
- 여러 독립 검증 항목을 하나의 boolean으로 합친다.

### `[개념 정리]`

- 데모가 증명하지 않은 성능이나 효과를 단정한다.
- 실제 검증 결과와 설명이 모순된다.
- 기준 버전, 환경 제약 또는 검증 범위를 누락한다.

## 7. 후속 설계 흐름

1. [전수 점검 절차](./18-demo-verification-audit-playbook.md)에 따라 241개 인벤토리를 작성한다.
2. 후보 유형별 데모 수, 예외와 UI 요구사항을 집계한다.
3. 최종 유형의 이름, 데이터 계약, 상태 표현과 공통 UI를 확정한다.
4. 유형별 골든 샘플을 선정한다.
5. 골든 샘플 구현과 검증 후 같은 유형의 데모를 묶어 수정한다.

## 8. 완료 기준

- 241개 모든 데모에 대표 유형 후보와 하나 이상의 검증 항목이 기록된다.
- 각 검증 항목에는 기대 결과, 증거 출처, 증거 위치와 판정 결과가 있다.
- 검증 불가와 실행 제약이 성공 또는 관찰 결과와 분리된다.
- 네 섹션별 수정 필요 여부, 사유, 심각도와 수정 방향이 기록된다.
- 전수 결과를 근거로 최종 검증 유형을 설명할 수 있다.
