# 13. 데모 [가이드] 섹션 최신화 및 정합성 검증 계획

241건 데모의 1단 `[가이드]` 섹션(`DemoGuideCard`)을 **실제 데모 동작과 일치하는 실행 절차**로 재작성하고, 어긋남을 자동으로 잡아내는 검증 장치를 세운다.

- **대상**: `packages/demo-kit/src/DemoGuideCard.tsx`와 이를 사용하는 241개 데모
- **선행 문서**: [09. 데모 표준 구조 및 4단 레이아웃 패턴](./09-demo-standard-and-layout-pattern.md), [10. 데모 감사 보고서](./10-demo-audit-report.md), [12. DeepDive 감사 보고서](./12-demo-deepdive-audit-report.md)
- **관련 규칙**: [`AGENTS.md`](../AGENTS.md) 규칙 15·23·24·25

---

## 1. 문제 정의

`[가이드]`는 학습자가 데모를 **어떤 순서로 조작하고, 그때 어떤 데이터를 관찰해야 하는지** 알려주는 유일한 진입점이다. 그런데 데모 본체(실습 화면·검증 패널·개념 정리)가 여러 차례 개선되는 동안 가이드는 그 변화를 따라가지 못했다.

핵심은 **가이드가 없는 게 아니라, 있지만 데모와 무관하다**는 것이다. 241건 전부 `DemoGuideCard`를 갖고 있으나(누락 0건), 그 내용 대부분이 카테고리 단위로 일괄 생성된 템플릿 문구다.

### 1-1. 실제 사례

`components/link/prefetch-options`의 현재 가이드 — 이 데모가 무엇을 하는지 한 글자도 설명하지 않는다.

```text
핵심 원리: Next.js 빌트인 컴포넌트 '<Link prefetch> 옵션 대조 (auto vs full vs false)'을
          활용하여 쇼핑몰의 성능, SEO, 폼 상호작용을 최적화하는 실무 구현입니다.
1. 컴포넌트 렌더링 점검 — 빌트인 컴포넌트가 생성한 최종 HTML 마크업과 속성을 확인합니다.
2. 동적 옵션 조작     — 옵션(속성)을 변경하며 브라우저 동작 및 네트워크 최적화 효과를 관찰합니다.
3. 최적화 결과 대조   — CLS 방지, 자동 포맷 변환, 폼 데이터 직렬화 결과를 검증합니다.
```

`CLS 방지`, `자동 포맷 변환`, `폼 데이터 직렬화`는 `next/image`와 `next/form` 이야기이며 이 데모에는 존재하지 않는다. 이 문구는 `components/*` 9개 데모에 **글자 하나 다르지 않게** 들어가 있다.

### 2-3. 구조적 획일성

- **스텝 수가 3개로 고정**: 240건이 정확히 3스텝, 1건만 2스텝. 데모 복잡도와 무관하게 3으로 맞춰져 있다. 서브 라우트를 2개 이상 갖는 데모(17건)나 Server Action을 쓰는 데모(13건)도 3스텝이다.
- **가이드가 실제 UI 라벨을 인용하는 비율: 3/241 (1%)**. 학습자가 화면에서 눌러야 할 버튼 이름이 가이드에 등장하지 않는다.
- **가이드 ↔ 검증 패널 연결 부재**: 3단 `ExpectedActualPanel`이 무엇을 보여주는지 가이드가 안내하는 데모는 사실상 없다. 사용자가 요구한 "어떤 데이터를 확인하면 되는지"가 구조적으로 빠져 있다.

### 2-4. 즉시 고쳐야 할 출력 버그

| 유형 | 건수 | 내용 |
|---|---:|---|
| 템플릿 리터럴 유출 | 2 | `file-conventions/not-found/missing-product-404`, `file-conventions/dynamic-segments/single-param` — 문자열 안의 `${id}`가 치환되지 않고 화면에 그대로 출력된다 |
| HTML 엔티티 유출 | 214 파일 | `&lt;Link prefetch&gt;` 형태가 JSX 문자열에 들어가 화면에 `&lt;`로 노출된다 |
| 검증 패널 보일러 | 218 | `VerificationFooter`의 `defaultExpected`가 "…사양에 따른 정상 동작 및 상태 변화 관찰"로 동일하다 |

HTML 엔티티 유출은 가이드 밖에도 걸쳐 있으나 `concept`/`title` 문자열이 주 발생지이므로 본 계획에서 함께 처리한다.

### 2-5. 범위를 넘는 발견 — 실습 실체 부족 101건

가이드를 재작성하려면 **쓸 실행 절차가 실제로 존재해야 한다.** 가이드·검증 푸터를 제외한 실습 코드만 측정한 결과:

- 실습 LOC < 120 **이면서** 상호작용 요소(button/input/Link) 2개 이하: **101건**
- 상호작용 요소가 아예 0개: **48건**
- 버튼이 0개: **64건**

`guides/authentication/middleware-guard`의 실습 컴포넌트는 16줄이며, `useState` 하나로 텍스트를 갈아 끼운다 — 실제 미들웨어 리다이렉트가 일어나지 않는다([`AGENTS.md`](../AGENTS.md) 규칙 24 위반). `components/link/prefetch-options`의 실습은 조작 불가능한 정적 텍스트 박스 3개다.

**이 101건은 가이드 문구만 고쳐서는 해결되지 않는다.** 조작할 것이 없는 화면에 정직한 실행 절차를 쓰면 "1. 화면을 읽는다"가 되기 때문이다. 본 계획은 이들을 별도 트랙으로 분리해 실습 보강과 함께 처리하며, 그 판단은 3-2에서 정한다.

## 3. 개정 전략

### 3-1. 가이드 품질 표준 (골든 샘플)

`mutating-data/optimistic-cart`가 현재 가장 좋은 가이드이며, 이를 표준으로 삼는다.

```text
핵심 원리: 네트워크 지연(800ms)이 있는 환경에서도 useOptimistic을 적용하면 버튼을 누르는
          즉시(0ms) 장바구니 수량과 총액이 먼저 올라가며, 백그라운드 서버 통신이 끝나면
          확정 데이터로 매끄럽게 교체됩니다.
1. [+ 장바구니 담기] 클릭      [0ms 즉각 반영]  — 상품 카드에서 담기 버튼을 클릭합니다.
2. 낙관적 임시 뱃지 확인       [useOptimistic]  — 목록에 주황색 [낙관적 렌더링] 뱃지가 표시되며 서버 통신(800ms)이 진행됩니다.
3. 서버 확정 상태 전환         [서버 확정 완료] — 800ms 후 Server Action이 완료되어 실제 서버 확정 상태로 전환되는 것을 확인합니다.
```

여기서 추출한 **필수 조건 5가지**:

| # | 조건 | 판정 방법 |
|---|---|---|
| G1 | `concept`은 이 데모에서만 성립하는 인과를 1~2문장으로 쓴다. 카테고리 일반론 금지 | 템플릿 지문 사전과 대조 |
| G2 | 스텝 제목에 **화면에 실제로 존재하는 라벨**을 `[대괄호]`로 인용한다 | 실습 컴포넌트에서 추출한 라벨 집합과 문자열 대조 |
| G3 | 스텝 수는 실제 조작 단계 수를 따른다. 3개 고정 금지 (2~6 허용) | 상호작용 요소 수와 교차 확인 |
| G4 | **마지막 스텝은 관찰 대상을 명시한다** — 어떤 값이, 어디서, 어떻게 바뀌는지 | `observe` 필드 필수화(3-3) |
| G5 | 수치·지연·상태명 등 구체값을 쓴다 (`800ms`, `307`, `stale`) | 숫자 또는 API 식별자 포함 여부 |

| 트랙 | 조건 | 건수 | 처리 |
|---|---|---:|---|

| **T3** 정합성 보정 | 고유 작성이나 라벨 불일치 | 41 | 현재 UI와 대조해 문구 교정 |

**T2 100건에 대한 범위 판단**: 사용자 요청은 가이드 최신화이므로, T2에서도 **가이드 재작성은 전량 수행한다.** 다만 실습이 정적 화면인 데모는 가이드가 정직해질수록 "볼 것이 없다"는 사실이 드러난다. 따라서 T2는 두 단계로 나눈다.

- **T2-a (가이드 우선)**: 현재 실습 화면이 실제로 보여주는 것만으로 절차를 쓴다. 없는 조작을 지어내지 않는다.
- **T2-b (실습 보강)**: 규칙 24를 위반하는 가짜 시뮬레이션을 실제 라우트·Server Action으로 교체한 뒤 가이드를 다시 쓴다.

T2-b는 데모 본체 개편이므로 **본 계획의 필수 범위가 아니다.** M5에서 대상 목록과 우선순위만 산출해 후속 작업으로 넘긴다. 이 판단은 사용자 확인이 필요한 지점이다(9절).

### 3-3. `DemoStep` 스키마 확장

사용자 요구 "어떤 데이터를 확인하면 되는지"를 구조적으로 강제하기 위해 선택 필드를 추가한다.

```ts
export interface DemoStep {
  step: number
  title: string
  description: string
  actionBadge?: string
  /** 이 단계에서 학습자가 관찰할 대상 — 어떤 값이 어디서 어떻게 바뀌는가 */
  observe?: string
  /** 관찰 위치. 3단 검증 패널을 가리킬 때 'verification' */
  observeAt?: 'playground' | 'verification' | 'devtools' | 'network' | 'console'
}
```

- 기존 241건은 `observe` 없이도 컴파일된다(하위 호환).
- 렌더링: `observe`가 있으면 스텝 하단에 `관찰 →` 접두사로 한 줄 덧붙인다. `observeAt`은 우측에 작은 위치 배지로 표시한다.
- **G4에 따라 각 데모의 마지막 스텝에는 `observe`를 필수로 채운다.** 이것이 3단 `ExpectedActualPanel`과 1단 가이드를 잇는 연결 고리다.

`DemoGuideCard.tsx` 렌더링 변경은 카드 전체 레이아웃을 바꾸지 않으며, 규칙 25의 4단 구조는 그대로 유지된다.

## 4. 작성 절차 (데모 1건 기준)

재작성은 추측이 아니라 **코드 판독**으로 한다. 데모 1건에 대해 다음 순서를 고정한다.

1. **실습 실체 판독** — `components/*.tsx`, `actions.ts`, 서브 라우트 `page.tsx`를 읽고 조작 가능한 요소(버튼·입력·링크·폼)와 그 라벨을 목록화한다.
2. **상태 전이 추적** — `useState`/`useOptimistic`/`useActionState`/Server Action이 어떤 값을 어떻게 바꾸는지, 지연·재검증 타이밍이 있는지 확인한다.
3. **검증 패널 판독** — `VerificationFooter`의 `expected`/`actual`이 무엇을 대조하는지 확인한다. 이것이 마지막 스텝의 `observe`가 된다.
4. **문서 대조** — 해당 데모의 `doc` 필드가 가리키는 `nextjs-docs/` 원문과 API 스펙을 대조한다. 불확실하면 `next-devtools` MCP로 `next@16.3.1` 1차 출처를 확인한다(규칙 21).
5. **작성** — G1~G5를 충족하도록 `concept`과 스텝을 쓴다. 스텝 수는 1에서 찾은 조작 단계 수를 따른다.
6. **자기 검증** — 6-1 스크립트를 해당 데모에 돌려 통과를 확인한다.

## 6. 자동 검증 장치

수작업 재작성 216건은 사람 눈으로 회귀를 막을 수 없다. 진단에 쓴 정적 분석을 **영구 검증기**로 승격한다.

### 6-1. 가이드 정합성 검증 스크립트

`packages/test-suite`에 `guide-consistency` 검사를 추가한다. 데모 디렉토리를 파싱해 다음을 판정한다.

| ID | 규칙 | 실패 조건 |
|---|---|---|
| GC01 | 템플릿 지문 금지 | 알려진 템플릿 문구 사전과 완전 일치 |
| GC02 | 스텝 제목 중복 금지 | 동일 스텝 제목 3종 세트가 2개 이상 데모에서 반복 |
| GC03 | UI 라벨 인용 | 스텝 제목·설명이 실습 컴포넌트의 실제 라벨을 하나도 인용하지 않음 |
| GC04 | 관찰 대상 명시 | 마지막 스텝에 `observe`가 없음 |
| GC05 | 문자열 유출 | `${`, `&lt;`, `&gt;`, `&amp;`가 가이드 문자열에 포함 |
| GC06 | 스텝 수 하한 | 상호작용 요소가 3개 이상인데 스텝이 2개 이하 |
| GC07 | 구체값 | `concept`에 숫자·API 식별자가 하나도 없음 |

GC03은 라벨 추출이 JSX 구조에 의존하므로 **경고(warn)로 시작**해 M2 종료 시점에 오류(error)로 승격한다. 나머지는 처음부터 오류다.

### 6-2. 진단 리포트 산출

스크립트는 판정과 함께 카테고리별 통과율 리포트를 출력한다. 마일스톤 종료 시 이 리포트를 [10. 데모 감사 보고서](./10-demo-audit-report.md)와 같은 형식으로 남긴다.

### 6-3. 기존 검증과의 연결

- `pnpm check-types` — `DemoStep` 확장 후 9/9 패키지 통과 유지
- `pnpm test` — 기존 419 케이스 + `guide-consistency` 케이스 추가
- `pnpm build` — 5/5 타깃 통과 유지

## 9. 확인이 필요한 결정

- **T2-b(실습 보강 100건)를 본 작업에 포함할지.** 본 계획은 "가이드는 전량 재작성하되, 실습 코드 개편은 목록 산출까지"로 잡았다. 실습까지 함께 고칠 경우 작업량이 数 배로 늘어나며 사실상 데모 재구축에 가까워진다.
- **GC03 목표치 90%.** 라벨이 없는 정적 데모가 존재하는 한 100%는 달성 불가하다.
