# 02. 모노레포 구성 방식 조사와 선택

- 상위: [nextjs-app 작업 규칙](../AGENTS.md)
- 결정: [ADR 0002 — pnpm workspaces + Turborepo, catalog로 기준 버전 단일 고정](./adr/0002-pnpm-turborepo-catalog-pinning.md)
- 조사일: 2026-08-18

## 1. 먼저: 왜 모노레포인가

이 저장소에서 앱을 여러 개로 쪼개는 이유는 관리 편의가 아닙니다. **기술적으로 불가피**합니다.

Next.js 앱 하나에는 `next.config` 파일이 하나뿐인데, 학습 문서가 가르쳐야 할 개념 중 상당수가 **앱 전역 설정**입니다. 예를 들어 `cacheComponents`를 끈 상태와 켠 상태를 둘 다 보여줘야 하는데, 이건 스위치 하나로 두 상태를 동시에 만들라는 요구라서 한 앱으로는 성립하지 않습니다.

전체 충돌 목록과 zone 배분은 [03. 결합 구조 설계](./03-composition-architecture.md)에 있고, 이 경계 기준 자체는 [ADR 0001](./adr/0001-config-axis-as-app-boundary.md)에 기록했습니다.

**그래서 판단 기준은 이렇게 좁혀집니다:**

1. 여러 Next.js 앱이 **하나의 Next.js 버전**을 공유하도록 강제할 수 있는가
2. 여러 앱의 dev 서버를 **한 명령으로** 동시에 띄울 수 있는가
3. `nextjs-docs`의 md 변경이 앱 빌드 캐시를 **정확히 무효화**하는가
4. 학습 저장소에 **자기 자신을 배우는 부담**을 얼마나 얹는가

4번이 특히 중요합니다. 이 저장소의 주제는 Next.js입니다. 모노레포 도구를 배우느라 Next.js 학습이 밀리면 본말이 전도됩니다.

## 2. 후보 6가지

### 2-1. pnpm workspaces + Turborepo — **채택**

`pnpm-workspace.yaml`이 패키지 경계와 의존성 공유를 담당하고, `turbo.json`이 태스크 실행과 캐싱을 담당합니다. 역할이 깔끔하게 나뉩니다.

| 기준 | 평가 |
|---|---|
| 버전 강제 | ✅ **catalog** — 루트에 `next: 16.3.1` 한 번 적고 각 앱은 `"next": "catalog:"`. 앱마다 버전이 갈라지는 게 **문법적으로 불가능**해짐 |
| 동시 dev | ✅ `turbo dev` 하나로 전부. `persistent: true` |
| 캐시 무효화 | ✅ `dependsOn: ["^build"]` + `@study/docs` 패키지로 md 변경을 정확히 추적 |
| 학습 부담 | ✅ 설정 파일 2개. Next.js·Turborepo·Vercel이 같은 팀이라 조합 마찰이 사실상 없음 |

**약점**: `turbo.json`의 `inputs`는 패키지 상대 경로라 패키지 밖 파일을 직접 참조할 수 없습니다. 그래서 `nextjs-docs`를 워크스페이스 패키지로 편입하는 우회가 필요합니다 ([01. 구성 절차 3-4](./01-project-setup.md)).

### 2-2. npm workspaces + Turborepo

Turborepo 부분은 동일하고 패키지 매니저만 다릅니다.

| 기준 | 평가 |
|---|---|
| 버전 강제 | ⚠️ catalog 없음. `overrides`로 강제할 수 있지만 이건 "의존성 충돌 해결" 장치를 버전 선언 용도로 전용하는 것이라 의도가 드러나지 않음 |
| 동시 dev / 캐시 | ✅ 동일 |
| 디스크·설치 | ❌ `next`와 `react` 한 벌을 zone마다 복제. zone 6개면 무거움 |

**기각 사유**: 판단 기준 1번(버전 강제)을 문법 수준에서 보장하지 못합니다. 이 저장소에서 가장 중요한 기준입니다.

### 2-3. pnpm workspaces 단독 (Turborepo 없이)

| 기준 | 평가 |
|---|---|
| 버전 강제 | ✅ catalog 사용 가능 |
| 동시 dev | ❌ `pnpm -r dev`는 zone별 포트·출력 정리를 해주지 않음. `concurrently` 같은 걸 직접 붙여야 함 |
| 캐시 무효화 | ❌ 빌드 캐시 개념 자체가 없음 |
| 학습 부담 | ✅ 가장 가벼움 |

**기각 사유**: Multi-Zones는 rewrites 목적지가 **살아 있어야** 개발이 됩니다. 앱 하나만 띄우면 사이트가 반쯤 깨진 상태로 보이므로, 동시 실행은 편의가 아니라 필수 조건입니다.

### 2-4. Nx

의존성 그래프 시각화, 코드 제너레이터, 영향받은 프로젝트만 빌드하는 `affected`, 플러그인 생태계까지 기능 폭은 가장 넓습니다.

| 기준 | 평가 |
|---|---|
| 버전 강제 | ⚠️ 패키지 매니저에 위임 (pnpm과 함께 쓰면 catalog 가능) |
| 동시 dev / 캐시 | ✅ Turborepo보다 정교함 |
| 학습 부담 | ❌ 프로젝트 그래프, executor, generator, 플러그인 등 Nx 고유 개념을 함께 배워야 함 |

**기각 사유**: 판단 기준 4번. Nx의 강점(수십~수백 개 프로젝트의 그래프 관리, 코드 생성 자동화)은 zone 3~6개 규모에서 회수되지 않습니다. 반면 학습 저장소를 읽는 사람이 Next.js가 아닌 Nx 개념을 먼저 만나게 되는 비용은 즉시 발생합니다.

### 2-5. Yarn Berry (PnP)

| 기준 | 평가 |
|---|---|
| 버전 강제 | ⚠️ `resolutions`로 가능하나 npm `overrides`와 같은 문제 |
| 생태계 마찰 | ❌ PnP는 파일시스템에 `node_modules`를 만들지 않아, 경로를 직접 여는 도구와 부딪힌 이력이 있음 |
| 로컬 가용성 | ❌ 미설치 |

**기각 사유**: 이 저장소는 셸이 `nextjs-docs`의 md 파일을 **경로로 직접 읽습니다.** 모듈 해석 방식이 특이한 환경은 이 지점에서 굳이 위험을 늘립니다. `nodeLinker: node-modules`로 끄면 되지만, 그러면 Yarn Berry를 쓰는 이유 자체가 줄어듭니다.

### 2-6. Bun workspaces

| 기준 | 평가 |
|---|---|
| 설치 속도 | ✅ 가장 빠름 |
| 버전 강제 | ⚠️ catalog 유사 기능이 있으나 pnpm만큼 정착되지 않음 |
| 검증 폭 | ⚠️ Next.js 프로덕션 빌드·배포 조합의 실사용 사례가 상대적으로 적음 |
| 로컬 가용성 | ❌ 미설치 |

**기각 사유**: 학습 저장소는 **재현성**이 성능보다 우선입니다. 6개월 뒤 clone한 사람이 문서대로 따라 했을 때 같은 결과가 나오는 게 설치가 몇 초 빠른 것보다 중요합니다.

## 4. 결론

**pnpm workspaces + Turborepo.**

네 가지 근거 중 앞의 셋은 어느 저장소에나 해당하는 일반론이고, **네 번째가 이 저장소에서 결정적**입니다.

1. 로컬에 pnpm 10.33.0이 이미 있고, `.gitignore`가 이미 `.turbo/`와 `.pnpm-store/`를 무시하고 있습니다. 저장소의 원래 의도가 이 조합이었던 것으로 보입니다.
2. zone이 늘어도 `next`·`react`가 하드링크로 공유됩니다.
3. `turbo dev` 한 번으로 Multi-Zones 개발 환경 전체가 뜹니다.
4. **catalog가 "문서 기준 버전 = 앱 버전"을 사람의 규율이 아니라 도구의 제약으로 바꿉니다.** 지금 `nextjs-docs/README.md`는 기준 버전을 산문으로 적어두고 사람이 지키기를 기대하고 있습니다. catalog를 쓰면 zone 6개의 Next.js 버전이 **갈라질 수가 없습니다.** 291개 문서가 한 버전을 근거로 쓰인 저장소에서, 이 보장은 다른 어떤 기능보다 값어치가 큽니다.

## 5. 이 결정이 무효가 되는 조건

나중에 아래 중 하나라도 참이 되면 재검토합니다.

- zone이 15개를 넘어 `affected` 단위 빌드가 실제로 필요해질 때 → Nx 재검토
- 데모 앱이 Next.js가 아닌 프레임워크로도 만들어질 때 → 도구 중립성 재검토
- pnpm catalog가 폐기되거나 대체될 때 → 버전 고정 수단 재검토
