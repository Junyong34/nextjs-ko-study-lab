# 05. 남은 설계 질문

- 상위: [nextjs-app 작업 규칙](../AGENTS.md)
- 작성일: 2026-08-18
- 이 문서의 범위: 01~04와 ADR에서 **정해지지 않은 것들**. 나중에 계획을 이어서 세울 때의 출발점입니다.

정해진 것은 여기 없습니다. 결정은 [01](./01-project-setup.md)·[03](./03-composition-architecture.md)과 [ADR](./README.md)에 있고, 이 문서는 **아직 열려 있는 것만** 모읍니다.

## 지금까지 정해진 것 (요약)

이어서 읽는 사람이 문맥을 잡기 위한 한 문단입니다. 상세는 각 문서에 있습니다.

데모의 존재는 `packages/demos/demos.yaml`이 정하고([ADR 0004](./adr/0004-demo-list-as-source-of-truth.md)), md의 `demo` 코드펜스는 본문 **링크** 위치만 정합니다. 데모는 **언제나 독립 열람**으로 보며 문서 본문에는 심지 않습니다 — iframe이 있는 곳은 독립 열람과 랜딩 히어로의 대표 데모뿐입니다([06](./06-ui-and-screen-design.md)). 학습 문서 주소는 md 경로에서 번호만 뗀 형태(`/getting-started/caching`)이고, 데모 주소는 `/demo/{문서 파일명}/{데모명}`으로 둘 다 zone이 드러나지 않으며([ADR 0005](./adr/0005-hide-zone-from-learner-url.md)), 데모 앱은 `/zone/{슬러그}/…`에서 chrome 없는 순수 데모만 그립니다. `status`(`stub`/`wip`/`done`)가 학습자 노출을 제어하는 유일한 스위치입니다. 라우트 스텁은 미리 만들지 않고 목록만 먼저 채웁니다. 1차 작업은 **배관 증명 데모 2개 + 셸**로 시작해 배포 검증을 통과한 뒤 대량으로 갑니다. 화면은 페이지 타입 5종으로 나뉘고, UI 기반은 shadcn/ui입니다([ADR 0006](./adr/0006-shadcn-ui-as-ui-foundation.md)).

## A. 배관 증명 전에 정해야 할 것

여기서 막히면 첫 배포까지 못 갑니다.

### A-1. 배관 증명 데모 2개의 구체 내용

**정해진 것**: `demo-baseline`은 2.14 Server Actions, `demo-cache-components`는 1.8 Caching. 이 둘이 [03. 6-1](./03-composition-architecture.md) 표의 배포 전용 함정을 전부 건드려야 합니다.

**안 정해진 것**: 각 데모가 학습자에게 **무엇을 관찰시키는가**. 두 문서의 "예제 및 데모 설계" 섹션에 이미 초안이 있으니 거기서 출발하되, 배관 검증 항목(Server Action 호출 · 높이 변화 · 공유 컴포넌트 · `next/image` · 스토리지 키)을 모두 포함하도록 조정해야 합니다.

**주의**: 배관을 다 쓰려다 데모가 복잡해지면 첫 배포가 늦어집니다. 학습 내용은 최소로 두고 `status: wip`으로 배포 검증을 먼저 통과시킨 뒤 살을 붙이는 편이 낫습니다.

### A-2. 데모 공통 UI를 어느 패키지에 둘 것인가 — **해결됨**

**`@study/demo-kit`을 신설합니다** ([06. 7-4](./06-ui-and-screen-design.md), [ADR 0006](./adr/0006-shadcn-ui-as-ui-foundation.md)).

결정적 근거는 `@study/ui`의 성격이 확정된 것입니다. 거기에 shadcn 기반 헤더·좌측 트리·검색 팔레트가 들어가면서 **셸 전용 패키지**가 됐고, 데모 앱이 이걸 의존하는 순간 `transpilePackages`를 통해 그 코드가 전부 데모 앱 빌드로 끌려 들어옵니다. "데모 앱은 chrome을 그리지 않는다"는 규칙이 패키지 경계에서도 지켜져야 합니다.

| 패키지 | 담는 것 | 쓰는 곳 |
|---|---|---|
| `@study/ui` | shadcn 컴포넌트, 헤더, 좌측 트리, 우측 목차, 카드 | 셸만 |
| `@study/demo-kit` | 기대/실제 패널, 리셋 버튼, 높이 브릿지의 데모 쪽 절반 | 데모 앱 (셸은 타입만) |

### A-3. `demos.yaml`의 타입 검증 수단

YAML은 오타를 잡아주지 않습니다. `zone: cahce` 하나로 그 데모가 사라집니다.

**후보**: zod 스키마(런타임 검증 + 타입 추론) / JSON Schema(에디터 자동완성) / TypeScript 파일로 아예 전환.

**연관**: YAML을 고른 이유가 "사람이 손으로 훑고 grep한다"였습니다. `.ts`로 바꾸면 타입은 공짜지만 그 성질이 약해집니다.

### A-4. `gen-stubs`가 만드는 스텁의 최소 내용

스텁은 학습자에게 안 보이므로([03. 4-1](./03-composition-architecture.md)) 렌더 내용은 중요하지 않지만, **작업 시작점**이라 형태는 정해야 합니다. `page.tsx` 하나인가, 기대/실제 패널까지 미리 넣은 골격인가.

### A-5. 스모크 테스트 도구와 실행 지점

**정해진 것**: `done` 데모를 전부 방문해 200 응답과 화면에 `✗`가 없는 것을 확인 ([03. 4-8](./03-composition-architecture.md)).

**안 정해진 것**: 도구(Playwright / 단순 fetch + HTML 검사), 실행 지점(CI / 배포 후 / 로컬 pre-push), 그리고 **어느 환경을 때리는가**. 배포된 사이트를 때려야 배포 함정을 잡지만, 그러면 배포 후 실패라 되돌릴 게 이미 나가 있습니다.

### A-6. 문서 URL 규칙의 lint를 어느 패키지에 둘 것인가

**규칙 자체는 정해져 결정 문서로 옮겼습니다** — md 경로에서 번호 접두사만 제거하고 그대로 미러링합니다 ([03. 3-1 문서 URL은 md 경로를 미러링한다](./03-composition-architecture.md)).

**안 정해진 것**: 그 규칙을 지키는지 보는 검사 두 개를 어디서 돌릴지입니다.

| 검사 | 어기면 |
|---|---|
| 번호 제거 후 URL이 겹치는 md가 없는가 | 두 문서가 같은 주소를 주장해 하나가 사라짐 |
| 카테고리 폴더가 예약 세그먼트(`demo`·`zone`·`demo-static`)를 쓰지 않는가 | 그 카테고리 전체가 데모 라우팅에 먹힘 |

**후보**: `@study/docs`의 `build`(md를 훑는 김에 같이) / `@study/demos`의 `lint`(다른 데모 검사와 한자리에).

**정할 때 볼 것**: 이 검사는 `nextjs-docs`만 보면 되고 `demos.yaml`이 필요 없습니다. 그런데 `@study/demos`의 `lint`가 이미 `@study/docs`에 의존하고 있어([01. 3-4-1](./01-project-setup.md)) 한곳에 모으는 선택도 자연스럽습니다.

## B. 대량 단계 전에 정해야 할 것

배관이 증명된 뒤, 데모를 30~90개로 늘리기 전에 필요합니다.

### B-1. 데모 가능 여부 판정 패스 (231건)

데모 목록을 채우려면 문서마다 **"이 개념을 브라우저에서 보여줄 수 있는가"**를 먼저 판정해야 합니다. 현황입니다 (2026-08-19 기준).

| 상태 | 문서 수 |
|---|---:|
| `가능` | 40 |
| `불가` | 0 |
| `검토 예정` | 80 |
| **판정 라인 자체가 없음** | **151** |
| 합계 (`예제 및 데모 설계` 섹션 보유 학습 문서) | 271 |

**판정이 남은 것은 231건**입니다 — `검토 예정` 80건에, 판정 라인이 아예 없는 151건이 더해집니다.

**정해진 것 (표기 형식)**: `- 데모 가능 여부:` 줄은 반드시 `가능` / `불가` / `검토 예정` 중 하나로 **시작**합니다. 뒤에 부연은 자유입니다. 그리고 이 줄은 **가능 여부만** 판정합니다 — 언제 만들지는 `demos.yaml`의 `status`가 관리하므로 판정 자리에 시점만 적지 않습니다 ([nextjs-docs AGENTS.md](../../nextjs-docs/AGENTS.md)).

형식이 흐트러졌던 원인은 `AGENTS.md`가 "Phase 1에서는 '구현 예정'으로만 남겨도 됨"이라고 허용한 것이었습니다. 그래서 19건이 가능 여부 대신 **시점**을 적어 grep으로 셀 수 없었고, 151건은 아예 줄을 쓰지 않았습니다. 규칙을 고치고 19건은 `가능 (…)` 형태로 정규화했습니다.

**안 정해진 것 (판정 기준)**: 무엇을 보고 `가능`·`불가`를 가르는지입니다.

| 후보 기준 | 결과 |
|---|---|
| "브라우저에서 관찰 가능한가"만 | `distDir` 같은 빌드 설정은 전부 `불가`. 판정이 기계적이고 빠름 |
| "데모 없이도 이해되는가"까지 | 관찰은 가능해도 데모 가치가 낮으면 `불가`. 데모 수가 줄지만 판단이 주관적 |

**주의**: 151건을 채우는 것은 판정 기준이 정해진 뒤입니다. 기준 없이 채우면 나중에 전부 다시 봐야 합니다.

### B-2. 데모명 작명 규칙

`url`의 두 번째 세그먼트입니다. 지금은 예시만 있고 규칙이 없습니다 — `basic`, `use-cache-basic`, `no-cache-baseline`.

**정할 것**: 접미사 관습(`-basic`, `-compare`, `-baseline`), 대조짝의 이름 짓는 법, 한 문서에 데모가 하나뿐일 때도 `basic`을 붙이는지.

**주의**: 학습자에게 노출되는 주소이고, 나중에 바꾸면 문서 링크와 북마크가 깨집니다.

### B-3. 대조짝을 목록에서 어떻게 표현하나

`cacheComponents` 켠 것과 끈 것처럼 **나란히 봐야 의미가 있는** 데모 쌍이 많습니다. 지금은 이름으로만 갈리고 목록에는 관계가 없습니다.

색인이나 문서 하단 목록에서 둘을 붙여 보여주려면 `pair` 같은 필드가 필요할 수 있습니다. 스키마를 늘리기 전에, 그냥 `doc`이 같으니 인접해서 뜨는 것으로 충분한지 먼저 봅니다.

### B-4. 한 문서 안 데모 여러 개의 순서

`demos.yaml`의 배열 순서를 쓰기로 잠정 정했습니다. 파일이 길어졌을 때도 유지되는지, 아니면 명시 `order`가 필요한지는 실제로 늘려보고 판단합니다.

## C. 진행하며 정해도 되는 것

### C-1. `/demo` 색인의 시각적 구조

학습 순서로 정렬한다는 것만 정해졌습니다. 카테고리별 접기, 검색, 데모 개수 표시 등은 열려 있습니다.

### C-2. 독립 열람 chrome의 구성 요소

제목·설명·"문서로 돌아가기"는 정해졌습니다. 그 밖에 — 이전/다음 데모, 소스 코드 보기, 전체화면 토글 — 은 안 정했습니다.

### C-3. 배포 구성

zone당 Vercel 프로젝트를 만든다는 것 외에는 열려 있습니다. 프리뷰 배포에서 `ZONE_*_URL`을 어떻게 채우는지가 특히 미정입니다 — 프리뷰마다 도메인이 바뀌므로 `.env`에 고정할 수 없습니다.

### C-4. `nextjs-docs`의 `.webp` 자산 서빙

이전부터 열려 있던 것입니다. `public/`으로 복사하는 빌드 스크립트와 스트리밍 라우트 핸들러 두 가지가 후보이고 아직 안 골랐습니다 ([nextjs-app/AGENTS.md](../AGENTS.md)).

## D. 이번 결정이 새로 연 질문

방금 정한 것들 때문에 생긴, 아직 답이 없는 것들입니다.

### D-1. 셸이 `demos.yaml`을 읽는 시점

빌드타임에 정적으로 읽으면 `status`를 바꿀 때마다 **셸 재배포**가 필요합니다. 지금 설계는 어차피 같은 커밋에서 라우트와 status가 함께 가므로 문제가 없지만, "데모가 깨져서 급히 내려야 할 때" 재배포 한 번이 필요하다는 뜻입니다.

런타임에 읽으면 즉시 반영되지만 셸이 파일을 읽는 시점이 요청마다가 되어 캐싱을 다시 생각해야 합니다.

### D-2. `done` → `wip` 되돌리기

데모가 깨져서 내리면 문서 하단 목록에서 **링크가 조용히 사라집니다.** 학습자 입장에서 어제 있던 게 없어지는 것인데, 그게 맞는지 아니면 "점검 중" 표시가 나은지 안 정했습니다.

### D-3. 멀티 라우트 데모의 고아 라우트

lint는 진입점만 검사하기로 했습니다 ([03. 4-7](./03-composition-architecture.md)). 그러면 데모를 지웠을 때 하위 라우트가 남아도 아무도 모릅니다. 진입점 아래 전체를 소유로 보고 대조할지 정해야 합니다.

### D-4. 캐시 태그 접두사 lint의 구현 방법

정규식으로 `cacheTag('…')` 문자열을 훑을지, AST를 볼지. 변수로 넘기는 경우(`cacheTag(tagName)`)를 어떻게 다룰지가 관건입니다. 너무 엄격하면 데모 코드가 부자연스러워지고, 학습자가 보는 코드라 그 대가가 큽니다.

### D-5. 2.43 Multi-zones 문서의 데모

셸이 chrome을 그리면서 학습자의 zone 경계 넘기가 사라졌습니다 ([03. 5절](./03-composition-architecture.md)). 이 문서는 이제 자기 데모를 따로 가져야 하는데, 무엇을 보여줄지 안 정했습니다.

## E. 04 검증에서 미확인으로 남은 것

[04. 설계 실현 가능성 검증](./04-feasibility-verification.md)의 "미해결 / 확인 불가"가 그대로 열려 있습니다. **"문제가 없다"가 아니라 "1차 출처로 확인하지 못했다"**입니다.

| 항목 | 상태 |
|---|---|
| 경로형 `assetPrefix` + Turbopack의 16.x 결함 | 공개 이슈를 찾지 못함 (없다는 뜻이 아님) |
| Tailwind v4 `@source` 상대 경로 규칙 | 계산은 맞지만 1차 출처 미확인 |
| `.next/dev/` 존재 여부 | `turbo.json`의 부정 glob이라 틀려도 무해 |
| `demo-export` 배포 시 rewrite 목적지 동작 | 실제 배포로만 확인 가능 |
| iframe 안 `use cache` 데모의 캐시 동작 | 코드가 없어 검증 불가 |
| `ResizeObserver` + `postMessage` 브릿지 실동작 | 구현 전 |

A-1의 배관 증명 데모가 이 중 여럿을 한 번에 닫습니다.
