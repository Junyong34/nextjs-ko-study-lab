# 241개 데모 검증 전수 점검 절차

[데모 검증 유형 분석 및 개선 설계](./17-demo-verification-type-design.md)의 후보 유형을 241개 실제 데모에 적용하고, 최종 검증 유형과 페이지 수정 목록을 도출하기 위한 실행 절차다.

## 1. 산출물

- 241개 데모 전수 인벤토리
- 후보 유형별 분포와 예외 목록
- 최종 검증 유형 제안
- 네 섹션별 수정 대상과 우선순위
- 실패·검증 불가·유형별 골든 샘플의 실행 증거

인벤토리는 [인벤토리 템플릿](./planning/demo-verification-inventory-template.md)을 단일 형식으로 사용한다.

## 2. 실행 전 고정 조건

점검을 시작할 때 다음 값을 인벤토리 머리말에 기록한다.

- Git 커밋과 브랜치
- Next.js 기준 버전
- 브라우저와 버전
- 운영체제
- 실행한 zone과 포트
- 개발 또는 프로덕션 모드
- 필요한 환경변수의 설정 여부
- 점검 일시

데모 사이에 쿠키, localStorage, sessionStorage, 캐시, 서버 메모리와 URL 상태가 이어질 수 있다. 각 데모의 초기화 방법을 먼저 확인하고, 초기화 방법이 없거나 완전하지 않으면 그 자체를 수정 대상으로 기록한다.

## 3. 1차 정적 분석

241개 데모를 실행하기 전에 코드와 문서를 읽어 인벤토리 초안을 만든다.

1. `demos.yaml`에서 URL, 제목, 문서, zone과 상태를 가져온다.
2. `DemoGuideCard`의 절차, 조작 라벨, `observe`, `observeAt`을 추출한다.
3. 데모 진입점과 실제 조작 컴포넌트에서 상태와 Next.js 경계를 확인한다.
4. `ExpectedActualPanel`과 `VerificationFooter`가 받는 값과 성공 조건을 확인한다.
5. 기대 결과 문구마다 실제 증거 출처가 있는지 연결한다.
6. 대표 검증 유형과 세부 검증 항목 유형을 임시 배정한다.
7. 고정 성공 문구, 상수 판정, 자체 상태 재진술과 과장된 성능 수치를 문제 후보로 표시한다.

정적 분석만으로 정상 판정을 내리지 않는다. 이 단계의 모든 결과는 실제 실행 전 후보 값이다.

## 4. 2차 전수 실행

각 데모를 다음 순서로 한 번 이상 실행한다.

1. 데모를 명시된 초기 상태로 되돌린다.
2. 가이드 문장을 한 단계씩 그대로 따른다.
3. 각 단계의 실제 조작 가능 여부와 UI 라벨 일치를 확인한다.
4. 가이드가 지정한 위치에서 변화를 확인한다.
5. 검증 항목별 증거를 데모 화면, URL, Network, 콘솔, 서버 로그, 소스, 빌드 산출물 또는 배포 환경에서 수집한다.
6. 기대 결과와 증거를 비교해 결과 상태를 기록한다.
7. 현재 `[검증]`이 실제 결과를 정직하게 표현하는지 확인한다.
8. `[개념 정리]`의 설명이 데모와 증거가 보여주는 범위를 넘지 않는지 확인한다.
9. 네 섹션별 수정 필요 여부와 사유 코드를 기록한다.
10. 다음 데모에 영향을 줄 상태를 초기화한다.

## 5. 증거 원칙

- 실습 화면을 그리는 동일한 로컬 상태를 그대로 실제값으로 반복하는 것은 독립 증거로 보지 않는다.
- 서버 응답, URL, 브라우저 API, 캐시 식별자와 실제 파일·산출물처럼 기능 경계를 통과한 값을 우선한다.
- 화면 관찰형은 통과 수치를 만들지 않고 관찰 대상, 조작 전 모습과 성공 단서를 기록한다.
- 빌드·배포 주장은 해당 환경에서 실행하지 못했다면 `blocked-by-environment`로 기록한다.
- `0ms`, `100%`, `80% 절감` 같은 정량 주장은 실제 측정 근거가 없으면 검증 불가 또는 문구 수정 대상으로 판정한다.
- 간접 증거를 사용할 때는 무엇을 직접 증명하지 못하는지 함께 기록한다.

## 6. 증거 파일 보관

모든 정상 데모의 스크린샷을 저장하지 않는다. 다음 경우에만 증거 파일을 남긴다.

- `fail`, `unverifiable`, `execution-error`, `blocked-by-environment`
- 후보 유형별 대표 사례
- 최종 유형의 골든 샘플 후보
- 동일 결과의 해석이 둘 이상 가능한 사례

파일명에는 데모 URL, 검증 항목 번호와 결과를 포함한다. 인벤토리에는 저장소 기준 상대 경로를 기록한다. 민감한 쿠키, 헤더와 환경변수 값은 캡처 전에 가린다.

## 7. 섹션별 사유 코드

| 코드 | 섹션 | 의미 |
|---|---|---|
| `G01` | 가이드 | 실제 UI 라벨과 절차 문구 불일치 |
| `G02` | 가이드 | 관찰 대상 또는 위치 누락 |
| `G03` | 가이드 | 초기화·새로고침·외부 도구 조건 누락 |
| `D01` | 데모 예제 | 가이드 절차대로 실행되지 않음 |
| `D02` | 데모 예제 | Next.js 동작을 로컬 상태로 모사함 |
| `D03` | 데모 예제 | 검증에 필요한 증거 신호 없음 |
| `D04` | 데모 예제 | 초기화 또는 환경 격리 실패 |
| `V01` | 검증 | 실제 측정값이 아닌 고정 문구 사용 |
| `V02` | 검증 | 근거 없는 성공·실패 판정 |
| `V03` | 검증 | 데모 특성과 검증 형식 불일치 |
| `V04` | 검증 | 여러 검증 항목을 단일 결과로 축약 |
| `V05` | 검증 | 증거 위치 또는 검증 범위 미표시 |
| `C01` | 개념 정리 | 데모가 증명하지 않은 효과를 단정 |
| `C02` | 개념 정리 | 실제 동작 또는 검증 결과와 모순 |
| `C03` | 개념 정리 | 기준 버전·환경·검증 범위 누락 |

심각도는 다음 기준을 사용한다.

- `high`: 학습자가 잘못된 Next.js 동작을 배우거나 검증 성공을 오인한다.
- `medium`: 절차를 완료할 수 없거나 중요한 증거를 확인할 수 없다.
- `low`: 의미는 유지되지만 문구, 위치 또는 보조 설명을 고쳐야 한다.
- `none`: 수정이 필요하지 않다.

## 8. 최종 유형 확정 회의

241개 실행이 끝난 뒤 검증 항목을 후보 유형별로 모아 다음 질문에 답한다.

1. 같은 데이터 계약과 UI로 표현 가능한 유형은 무엇인가?
2. 한 후보 유형 안에서 판정 방식이 달라 분리해야 하는 사례가 있는가?
3. 외부 도구·환경 확인은 독립 유형인가, 증거 위치인가?
4. 자동 판정과 화면 관찰을 한 패널에서 어떻게 구분해야 하는가?
5. 검증 불가 데모는 데모를 재설계할 것인가, 기대 범위를 줄일 것인가?
6. 최종 유형별 골든 샘플로 어떤 데모를 사용할 것인가?

이 회의 결과로 최종 유형, 상태 모델, 공통 컴포넌트 계약과 마이그레이션 묶음을 별도 구현 계획에 작성한다.

## 9. 전수 점검 완료 기준

- `demos.yaml`의 241개 항목과 인벤토리가 일대일로 대응한다.
- 모든 가이드 절차를 실제로 실행했거나 실행하지 못한 환경 사유가 기록돼 있다.
- 모든 검증 항목에 후보 유형, 증거 출처, 증거 위치와 결과가 있다.
- 네 섹션별 수정 판정이 누락 없이 작성돼 있다.
- 실패·검증 불가·대표 사례의 증거가 인벤토리와 연결돼 있다.
- 후보 유형의 병합·분리·제거 근거와 최종 유형 제안이 작성돼 있다.
